    two-player, turn-based, zero-sum games

    Up to now we've been considering a single agent maximizing a single objective function, where the net change to that objective function after every step is given by the reward function. It turns out we can pretty easily extend MDPs to account for more than one objective function. In the jargon of game theory, I'll introduce a concept called a "two-player, turn-based, zero-sum game." A two-player game means there are exactly two agents, each maximizing their own objective function. A turn-based game means only one agent can take an action in a given state, and the right to act switches with every action. We will refer to this agent as the "side to move" of a state. Finally, a zero-sum game means that the gains of one agent equal exactly the losses of the other agent.

    In particular, \(\mathcal{S}, \mathcal{A}\), and \(\mathcal{T}\) remain the same, except now each state \(s \in S\) also has a "side to move" associated with it. But now, we let \(R(s, a, s')\) be the net change to the objective function belonging to the side to move of \(s\) after taking action \(a\) from state \(s\) and landing in state \(s'\), which is exactly the opposite of the net change to the objective function belonging to the side to move of \(s'\), since the game is zero-sum. In other words, zero-sum means that both players essentially have the same objective function, and one player is trying to maximize it and the other player is trying to minimize it.

    Naturally, the optimal policy \(\pi^*(s)\) is the action which maximizes the expected value of the objective function belonging to the side to move of \(s\). The associated Bellman equations are therefore:

    \[ \pi^*(s) = \arg\max_{a \in \mathcal{A}(s)} Q^*(s, a) \]
    \[ V^*(s) = \max_{a \in \mathcal{A}(s)} Q^*(s, a) \]
    \[ Q^*(s, a) = \sum_{s' \in \mathcal{S}}\mathcal{T}(s, a, s')(\mathcal{R}(s, a, s') - V^*(s')) \]

    The only thing that changes is the negative sign in front of \(V^*(s')\), representing the adversarial zero-sum nature of the game.

    chess

    For reasons we'll get into later, we want to represent chess as an MDP. Well, chess is naturally a two-player, turn-based, zero-sum game. We can let each state \(s \in \mathcal{S}\) be a chess position. Actions \(a \in \mathcal{A}(s)\) are legal chess moves. Chess moves are deterministic, so transition probabilities \(\mathcal{T}(s, a, s')\) are zero for all \(s'\) except for one. For simplicity, denote this position as \(s' = T(s, a)\). All we care about is the final outcome, so rewards \(\mathcal{R}(s, a, s')\) are zero except for when \(s'\) is a terminal state. If \(s'\) is checkmate, then \(\mathcal{R}(s, a, s')\) is \(1\). If \(s'\) is a draw, then \(\mathcal{R}(s, a, s')\) is \(0\). The action value simplifies to

    \[ Q^*(s, a) = \mathcal{R}(s, a, s') - V^*(s'), \quad s' = T(s, a) \]

    \(V^*(s)\) can equal either -1, 0, or 1. \(V^*(s) = 1\) if the side to move of \(s\) has the ability to force a win no matter the opponent's moves. \(V^*(s) = -1\) if the side to move of \(s\) has no ability to prevent a loss if the opponent makes the right moves. \(V^*(s) = 0\) if neither is true.

    why?

    I promised I'd answer the question: "Why do we want to formulate chess as an MDP?" The answer is that we want to use Monte Carlo tree search to compute the best move! Well, if you're a smart guy or gal, you'd ask: "Why do we want to use Monte Carlo tree search to compute the best move?"

    minimax search

    If you look at the Bellman equation for chess, it's quite simple. In fact, there's no "expectation" to even compute! It's merely a matter of considering all sequences of legal moves, and checking whether or not a player can force a win. One could program an exact solution to this MDP with something like

    def compute_value(pos):
    if is_checkmate(pos):
        return -1
    if is_draw(pos):
        return 0
    value = float('-inf')
    for move in legal_moves(pos):
        next_pos = make_move(pos, move)
        value = max(value, -compute_value(next_pos))
    return value

    However, if you know anything about chess, you'd know that the number of sequences of legal moves is astronomically large for most positions. What one can do is create a heuristic function which outputs a number in \([-1, 1]\) which is a guess for the value of the current position. It is allowed to be outside of -1, 0, and 1 to allow for uncertainty. The closer the heuristic is to 1 the closer the position should be to being winning for the current side to move, and vice versa. This heuristic is usually hand-coded by chess experts to take into account things like the number of pieces left on the board and their locations. The idea is that this heuristic should become more accurate the closer the position is to being terminal. If you consider sequences of moves of a certain length (which can be manageable in size), you can assign their terminal value with the heuristic. Then the deeper you search, the more accurate your final result should be.

    def compute_value(pos, depth):
    if is_checkmate(pos):
        return -1
    if is_draw(pos):
        return 0
    if depth == MAX_DEPTH:
        return heuristic(pos)
    value = float('-inf')
    for move in legal_moves(pos):
        next_pos = make_move(pos, move)
        value = max(value, -compute_value(next_pos, depth + 1))
    return value

    This idea is known as minimax search, and it is exactly how essentially all dominant chess engines worked for the majority of computer science history.

    deep neural networks

    In 2012 with the release of AlexNet, deep neural networks began to become the dominant force in artificial intelligence. In fact, with a big enough dataset of previously analyzed chess positions, one can easily train a deep neural network that greatly outperforms any hand-coded heuristic function from the previous section in terms of accuracy. However, at least two things go wrong if one attempts a replacement:

    1. There is a massive tradeoff with speed. Deep neural networks are typically much more computationally intensive than a hand-coded heuristic, so the number of positions analyzed must be cut down greatly. In minimax search this means that the depth must be decreased.

    2. Deep neural networks are inherently noisy. Minimax search computes the exact maximum at every step, meaning that one single noisy evaluation in the wrong line could throw the algorithm off the best move.

    I propose that Monte Carlo tree search is much more compatible with these two things. Look at step 3 in the algorithm at the bottom of the previous post: simulation. It should be well agreed upon that such a random rollout is already quite computationally intensive and highly variable. Suppose that one replaced such a rollout with a neural network that predicts the expected result, similar to the way we used a heuristic in minimax. Then:

    1. Since we are greatly limited in our search, common sense would say to spend more time considering sequences of moves that are likely to be played on the board. Minimax search considers all sequences to roughly the same depth. Monte Carlo tree search naturally searches the most promising sequences the deepest due to the UCB metric.

    2. In Monte Carlo tree search, action values are taken as the average of the reward estimates evaluated stemming from a particular move. Therefore the inherent noise from the deep neural network is almost completely averaged away.

    policy + upper confidence bound

    While it's true that Monte Carlo tree search is naturally good at spending more time searching promising variations, it's also true that often quite a large number of iterations is needed before the algorithm starts to do this. At the beginning of the search, all of the exploration terms are high, and hence bad moves are searched almost as much as good moves are.

    Since every expanded node gets fed into a deep neural network initially, it's cheap to add a policy head which outputs a probability distribution \(P(s, a)\) over the legal moves \(a \in A(s)\), predicting the actions that are likely to be good. If we penalize the exploration terms of low probability moves, then we tend to get our desired behavior more quickly, making the algorithm more efficient. First introduced in a paper called Multi-armed Bandits with Episode Context and reformulated in the AlphaZero paper, was a reformulation of the upper confidence bound called the Policy + Upper Confidence bound for Trees (PUCT)

    \[ PUCT(s, a) = Q(s, a) + c_{\text{puct}}P(s, a)\sqrt{\frac{\ln(N(s))}{N(s, a)}} \]
    algorithm

    An algorithm to implement Monte Carlo tree search with PUCT for chess would look like this. We store the tree in memory, which grows in size as the algorithm runs. Each node in the tree stores the following information:

    • \(N(s)\), the number of simulations which reached node \(s\), initialized to 0.
    • For all actions \(a\) from node \(s\): \(N(s, a)\), the number of times action \(a\) was taken from node \(s\) over all simulations, initialized to 0.
    • For all actions \(a\) from node \(s\): \(Q(s, a)\), the empirical average action value over all simulations, initialized to 0.
    • \(V(s)\), the estimated value of \(s\), computed by the deep neural network when the node is initialized.
    • For all actions \(a\) from node \(s\): \(P(s, a)\), the policy value of action \(a\), computed by the deep neural network when the node is initialized.

    The tree starts out as only the root node. Repeat the following steps until time runs out:

    1. Selection: Start from the root node \(s\). If any action from \(s\) is unexplored, choose the one with the highest policy value. If all actions from \(s\) have been explored, then let

      \[ a^*(s) = \arg\max_{a \in \mathcal{A}(s)} PUCT(s, a) \]

      and take action \(a^*(s)\). After taking \(a^*(s)\), you reach a new state \(s'\). Repeat this selection process until an unexplored state is reached.

    2. Expansion: If an unexplored state \(s_N\) is reached, then add it to the tree.

    3. Backpropagation: For each state-action pair \((s_i, a_i)\), \(i = 0, \ldots, N - 1\), in the traversal leading to \(s_N\), perform the following updates

      \[ N(s_i) \leftarrow N(s_i) + 1 \]
      \[ N(s_i, a_i) \leftarrow N(s_i, a_i) + 1 \]
      \[ Q(s_i, a_i) \leftarrow Q(s_i, a_i) + \frac{(-1)^{T - i} V(s_T) - Q(s_i, a_i)}{N(s_i, a_i)} \]

    Once you are done searching, choose the action \(a\) such that \(Q(s, a)\) is the highest.

    chess, again

    If you know about my interests in programming, you know I've always been obsessed with programming a chess engine from scratch. In 2023, I learned C++ just so I could give it a shot, and I loved every second of optimizing every line of code to run as fast as I could. Of course, I went for the old-fashioned approach of "crunch as many positions as you can" to find the best move.

    Whether I knew it or not at the time, I now realize that for an engine strategy like that, speed is much less important than smart things such as better heuristics for pruning more branches of the search tree. I was more interested in making things fast than making them smart.

    I often fall into the pitfall of premature optimization, and while it's fun, I know now how damaging it can really be. I think my focus has now shifted more towards writing clean code than hyper- optimized code. I spend too much time thinking about how my code looks, or how "professional" it is. It's a major time-waster, but hey, I program for fun, and the end result is always worth it to me.

    I think that around the time my paradigm shifted, I decided to completely rewrite my original chess engine. I changed the core design principles. My original attempt was completely object-oriented and full of encapsulation. I had just taken the class "Object Oriented Programming" in college. It took me about a year to realize that I despised it. I had also started to get really into legacy C code. I adopted procedural programming with structs, and I found it greatly satisfying. I felt like a professional and I felt in control. With this new control, along with some classy improvements like bitboards, I saw some serious improvements. However, I got busy with school and never really finished the job, although I still really love the code I wrote.

    As I stepped back into the modern world, I started to get really into fancy tooling. Programming in Python forced me to adopt modern workflows, and I got really addicted. Also, as much as I loved my second iteration, I used CMake and, god, I HATED IT. It all felt ancient. And of course, my main gig is Python and so I tried to incorporate it into my chess project: building and training neural networks that I could implement into my engine. But wrangling with ctypes also absolutely sucked. So now that I have time to get back into this project, as much as I love the code that I wrote the second time around, I just can't see myself getting back into it.

    This brings me to today. As crazy as it sounds, I'm gonna rewrite my engine from scratch for the SECOND TIME. But there are several things that I am going to do different. First, I'm gonna stick to what I am really interested in, machine learning. This'll heavily rely on deep neural networks to do the heavy lifting. So although I do want a fast lower layer, I am not going to kill myself with optimizations. Second, to satisfy my modern tastes, I am going to try out a fancy new modern language with lots of buzz, Rust. It looks really attractive to me. First of all, Cargo looks fantastic. And with things like PyO3 and maturin, I am GIDDY with the anticipation of baking this directly into my favorite language, Python. Second of all, the language's strict rules really tickle my obsession with writing clean, professional code. And its speed with zero-cost abstractions makes my incessant premature-optimization devil happy.

    I've been obsessed with this AlphaZero paper by Google, and so my goal is to recreate it myself. I just got a fancy new M5 macbook pro, and so I really want to see how far I can take it by sticking to my hardware alone. I won't talk too much about it today, since I want to document the project on this blog. I just wanted to describe my journey up to this point.
